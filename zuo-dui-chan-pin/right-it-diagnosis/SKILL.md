# 区分正确的它与错误的它

## R — 原文 (Reading)

> 先确保你在构建“正确的它”，再确保你能把它构建正确。
>
> — Alberto Savoia, 第2章「正确的它」

---

## I — 方法论骨架 (Interpretation)

不要把“产品没成功”自动解释为执行不好。
作者把创意分成两类: 正确的它, 即执行到位后市场会响应; 错误的它, 即执行到位也没人要。
很多团队会继续优化设计、工程、营销和销售, 但真正的问题可能是产品前提不成立。
诊断时要先分清失败位置: 启动失败是触达/发布问题, 运营失败是体验/交付问题, 前提失败是市场根本不需要。
只有前两者适合继续修执行; 前提失败必须重新验证或调整创意。
这能防止团队把资源继续投入一个“做得更好也没人要”的方向。

## A1 — 书中的应用 (Past Application)

### 案例 1: 作者在谷歌访谈失败项目
- **问题**: 失败团队起初倾向于把责任归给产品、营销、销售或运营。
- **方法论的使用**: 作者追问真正失败原因, 将失败区分为启动、运营和前提。
- **结论**: 很多团队做对了执行, 但市场不想要这个产品。
- **结果**: 作者形成 FLOP 归因, 并提出先确认“正确的它”。

### 案例 2: 作者创业失败
- **问题**: 作者团队有资金、人才、计划和执行, 公司仍失败。
- **方法论的使用**: 他回看失败不是技术不行, 而是市场前提没有被真实验证。
- **结论**: 错误前提无法靠后续优化拯救。
- **结果**: 这成为本书方法论的起点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品上线后数据差, 用户问是否要继续打磨。
2. 用户复盘失败项目, 但原因全是“营销没做好”“功能还不够”。
3. 用户准备投入更多资源, 但市场反应还不清楚。
4. 用户问一个创意“到底是不是值得做”。

### 语言信号

- “是不是我们执行还不够好?”
- “这个产品没人用, 要不要继续优化?”
- “失败到底是渠道问题还是产品没人要?”
- “我们应该 pivot 还是继续做?”

### 与相邻 skill 的区分

- 与 `market-failure-prior` 的区别: 本 skill 做失败类型诊断; 后者设置评估新创意时的默认风险。
- 与 `tri-meter` 的区别: 本 skill 用于归因和分支判断; `tri-meter` 用于多次试验结果的证据映射。

## E — 可执行步骤 (Execution)

1. **定义预期市场成功**
   - 完成标准: 明确本来期待的结果, 如购买率、留存、收入、采纳率或传播。

2. **按 FLOP 诊断失败位置**
   - 完成标准: 分别检查启动问题、运营问题、前提问题, 每类至少列 1 条证据。

3. **判断是否为错误的它**
   - 完成标准: 若目标市场知道产品、理解产品、能体验产品却仍不投入切身利益, 标记为前提风险。

4. **给出行动分支**
   - 完成标准: 输出“修启动 / 修运营 / 重验前提 / 调整或放弃”之一, 并说明依据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 只是技术 bug、性能故障或交付事故, 已明确与市场需求无关。
- 用户尚未定义目标市场和期待行为, 应先调用 `market-engagement-hypothesis`。
- 没有任何真实市场接触, 不足以诊断失败位置, 应先调用 `xyz-hypothesis` 或 `pretotype-yoda`。

### 作者在书中警告的失败模式

- 互相指责掩盖前提失败。
- 用更多设计、工程和营销拯救错误前提。
- 把短期声量误判为长期市场需求。

### 作者的盲点 / 时代局限

- 长周期企业采购可能暂时无法用早期行为区分前提失败和销售周期问题。
- 强监管行业中, 市场想要也不代表可以合法或安全交付。

### 容易混淆的邻近方法论

- `escape-thoughtland`: 处理证据是不是意见。
- `adjust-before-pivot`: 在证据不理想后决定微调、翻转或放弃。
